## Goal
Clear the two M1 carry-overs that bite in M2: a DDL parser that silently ignores forms it does not
understand (so a mistyped migration could pass the consistency tests), and a db-test suite that
takes ~12 minutes because it creates a fresh Neon database per test. Both are test-infrastructure
only - no production code changes.

It sits in **wave 2, after T2.1a**, on purpose: the hardened parser must accept the real
`CREATE INDEX ... USING hnsw (...)` statements that 0003 and `schema.sql` now contain, so it needs
them to exist first.

## Contract
`tests/core/ddl_parser.py` keeps its current public shape, built on `core/sqlsplit.split_sql`. It
gains `DdlParseError`. No `northvaine/` file changes.

## Acceptance criteria
- [ ] `tests/core/ddl_parser.py` raises `DdlParseError` naming the offending statement on **any**
      `CREATE` / `ALTER` / `DROP` form it does not understand, instead of silently ignoring it
      (M1 carry-over 1). The message includes enough of the statement to find it.
- [ ] `tests/core/test_ddl_parser.py` proves the raise for at least **three** distinct unsupported
      forms, and proves the parser **accepts** the forms that now exist in the repository:
      `CREATE INDEX ... USING hnsw (col vector_cosine_ops)`, the `halfvec` expression-index form if
      T2.1a took the fallback branch, and `ALTER TABLE ... ADD COLUMN` for the four new `llm_calls`
      columns.
- [ ] `tests/core/test_schema_consistency.py` and the full default suite still pass unchanged
      against the hardened parser - i.e. the parser understands 100% of the real `schema.sql`.
      Shown by `uv run python scripts/gate.py` passing.
- [ ] `tests/db/conftest.py` reuses **one** migrated database for the whole db-test session (or
      uses `reuse` isolation mode) instead of creating a fresh database per test, per the M1
      DECISIONS entry on db-test isolation.
- [ ] `uv run python scripts/tasks.py db-test` passes against `TEST_DATABASE_URL` in materially
      less than the ~12 minutes (719 s) M1 measured. The new runtime, the server version and the
      pass count are recorded in the ticket report.
- [ ] **Isolation is not quietly traded away:** the db-test suite also passes in a randomized test
      order (e.g. `-p no:randomly` removed / `--random-order`, or an explicit reversed-order run),
      proving no cross-test leakage was introduced by the reuse. The command and its output go in
      the report.

## Invariants touched
- **Tests travel with code; no network in the default run** (FACTORY §2 rule 6). The db tests stay
  marked `db` and deselected from the gate.
- **A test is never weakened to make it pass**: the parser gets stricter here, not looser, and the
  speed change must be proven not to cost correctness.
