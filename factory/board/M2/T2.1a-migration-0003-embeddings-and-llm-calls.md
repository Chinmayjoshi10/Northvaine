## Goal
**Scope narrowed twice (3 Oct).** Migration 0003 itself, `schema.sql`, and the three tests that
assert the DDL are all owned by **T2.0** (FACTORY rule 9: whoever changes the DDL owns every test
that asserts it). What remains here is the *verification* that the dimension agrees everywhere and
that the live database matches: the offline 0003 render test, the `EMBED_DIM_EXPECTED` agreement
test, and the live schema test. This ticket writes **no migration and no DDL**.

If, when this ticket starts, T2.0 has already landed every assertion below, say so and close it as
empty rather than duplicating coverage.

**Prerequisite (orchestrator, not this builder):** probe P3 - one live `/v1/embeddings` call with
`dimensions=<N>` - must be recorded in
`docs/integrations/nemotron-embeddings-and-the-vector-dimension.md` with today's date, and the
value must already be in `northvaine/core/standards.EMBED_DIM_EXPECTED` from T2.0. **The dimension
is never a literal typed from memory.**

## Contract
Migrations must not read settings, so 0003 (written in T2.0) contains a literal dimension. The
literal is kept honest **here**, by an offline test asserting it equals `EMBED_DIM_EXPECTED` and
the value in `schema.sql`. Three places must agree: the migration literal, `schema.sql`, and
`core/standards.EMBED_DIM_EXPECTED`.

`LlmCallRow` (frozen in T2.0, including `provider` - D15) is the shape `llm_calls` must match.

## Acceptance criteria
- [ ] Migration 0003 sets `document_chunks.embedding`, `event_concepts.embedding` and
      `theses.embedding` to the confirmed dimension N and creates one HNSW cosine index per column,
      following this ladder exactly (the branch taken is stated in the migration docstring with N
      and its source):
      - **N <= 2000 (primary path):** column `vector(N)`, index
        `USING hnsw (embedding vector_cosine_ops)`.
      - **2000 < N <= 4000 (fallback):** column stays `vector(N)`, index is a `halfvec(N)`
        expression index with `halfvec_cosine_ops`.
      - **N > 4000: not acceptable.** pgvector cannot index it at all (fact 8: limits are 2,000 for
        `vector`, 4,000 for `halfvec`). Stop and re-probe with a smaller `dimensions` value.
      Cosine is correct because the embedding model L2-normalizes its output.
- [ ] Migration 0003 adds `run_id uuid`, `prompt_version text`, `latency_ms int` and `error text`
      to `llm_calls`, plus an index on `created_at` and one on `(workspace_id, created_at)` so the
      lifetime and daily budget sums never scan the table. `downgrade()` drops the indexes and
      columns and returns the three vector columns to the dimensionless `vector` type.
- [ ] `schema.sql` is updated to the same end state. Its header comment about dimensionless vectors
      is replaced by the confirmed dimension, the model it came from and the research doc + date.
- [ ] `tests/core/test_migration_0003_offline.py` renders 0003 offline in both directions and
      asserts: the sized vector type on all three columns, each index with its operator class, the
      four new `llm_calls` columns, the two new `llm_calls` indexes, and a `downgrade` that restores
      the dimensionless type.
- [ ] `tests/core/test_embed_dim_consistency.py` proves the dimension in `schema.sql`, the literal
      in migration 0003 and `core.standards.EMBED_DIM_EXPECTED` all agree, and that the value is
      `<= 2000` on the primary path (or `<= 4000` with a halfvec index on the fallback path). This
      is the offline guard that catches a drifted dimension without spending a cent.
- [ ] `tests/core/test_schema_consistency.py` still passes with `LlmCallRow` matching the extended
      `llm_calls` table, and its `test_every_check_in_list_has_a_matching_enum` now **fails with an
      assertion naming the missing model** instead of raising `AttributeError` from a bare
      `getattr` (M1 carry-over 2).
- [ ] `tests/db/test_schema_live.py`: the old `test_vector_columns_are_dimensionless` is replaced
      by a test asserting the live typmod equals the confirmed dimension on all three columns, and
      that each expected index exists on the live database with the expected access method.
- [ ] `uv run python scripts/gate.py` passes **with no database present** (the offline render still
      works). The db-marked tests stay deselected from the gate.

  parameter is not an optimization here - it is what makes the column indexable at all.
