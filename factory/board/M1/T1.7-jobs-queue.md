## Goal
A safe, simple work queue in Postgres. Every later funnel stage (discover, filter, ... judge)
runs as a job kind on it.

## Contract
Implement the frozen `northvaine/core/queue.py` signatures from PLAN.md. Do not change them.
The functions never commit. `run_worker` owns its transactions.

## Acceptance criteria
- [ ] `backoff_delay(attempts)` returns `min(max, base * 2**(attempts-1))` as a timedelta,
  with defaults from settings. It is pure, monotonic non-decreasing and capped. Unit-tested
  without a DB, including attempts 0 and 1 and a large value.
- [ ] `enqueue` inserts kind, payload, run_after (if given), workspace_id and
  `max_attempts = job.max_attempts or settings.job_max_attempts`, and returns the id.
- [ ] `claim` issues one statement, `UPDATE jobs SET status='running', attempts=attempts+1,
  locked_at=now(), locked_by=:worker WHERE id = (SELECT id FROM jobs WHERE status='queued' AND
  run_after <= now() [AND kind = ANY(:kinds)] ORDER BY run_after, id FOR UPDATE SKIP LOCKED
  LIMIT 1) RETURNING *`, and maps the row to `Job`. A unit test compiles it with the
  postgresql dialect and asserts `FOR UPDATE SKIP LOCKED`, `LIMIT` and `id = (`.
- [ ] `heartbeat`, `complete` and `fail` update only `WHERE id=:id AND status='running' AND
  locked_by=:worker_id`, and return whether a row matched:
  - `heartbeat` sets `locked_at=now()`;
  - `complete` sets `done` and `finished_at`;
  - `fail` requeues with `run_after = now() + backoff_delay(attempts)` and clears the lock
    while `attempts < max_attempts`. Otherwise it sets `failed` and `finished_at`. It stores
    the error truncated to 2,000 chars, after replacing any known secret value from settings
    with `***` (unit test).
- [ ] `requeue_stale(lease_seconds)` handles running jobs with
  `locked_at < now() - lease`: it marks them `failed` (error "lease expired") when
  `attempts >= max_attempts`, otherwise returns them to `queued` with the lock cleared. It
  returns `StaleResult(requeued, failed)`.
- [ ] `run_worker(handlers, worker_id, once=True)`:
  - claims in one `session_scope` and runs the handler outside any transaction;
  - completes or fails in a second scope;
  - fails an unknown kind with "no handler for kind '<kind>'";
  - treats a handler exception as fail, using the exception text;
  - returns the count.

  Unit-tested with a fake sessionmaker and fake handlers, no DB.
- [ ] `tests/db/test_queue_db.py` (marked `db`, on `migrated_url`) proves:
  1. `EXPLAIN (VERBOSE)` of the claim shows `InitPlan`;
  2. 2 concurrent claimers over 20 jobs never claim the same id, and claim all 20;
  3. retry with backoff, then a terminal failure at max_attempts;
  4. `complete` by a non-owner returns False and changes nothing;
  5. stale leases are requeued, or failed when attempts are exhausted;
  6. `heartbeat` prevents a requeue.
- [ ] No network libraries are imported. The T1.0 contract test passes. Gate passes.

## Invariants touched
- No secrets in stored errors.
- No network.
- Hard caps: max_attempts bounds the retries.

## Notes
- Claiming each row at most once relies on `id = (scalar subquery)` running as an InitPlan.
  That is community knowledge, so it is asserted by EXPLAIN in db-test.
- ORDER BY with SKIP LOCKED can return rows out of order under concurrency. That is
  acceptable, because ordering is best-effort.
- Handlers must be idempotent. A worker can lose its lease and the job can run twice.
