## Root cause of the T2.0 failure: a plan defect, not a builder mistake

The gate in the T2.0 worktree fails at the unit-test step:

```
tests/core/test_schema_consistency.py::test_row_models_match_tables
AssertionError: ['llm_calls.error: field of LlmCallRow has no column', ...]  (4 items)
1 failed, 285 passed, 15 deselected
GATE FAILED at step: unit tests
```

The four orphaned fields are exactly `run_id`, `prompt_version`, `latency_ms` and `error`.

This is the plan contradicting itself, and the builder followed it faithfully:

- **T2.0's acceptance criteria require** `LlmCallRow` to carry "the `LlmCallRow` fields matching
  schema v2 **plus the four columns T2.1a adds** (`run_id`, `prompt_version`, `latency_ms`,
  `error`)".
- **T2.1a, which adds those columns to `schema.sql` and migration 0003, is in wave 1** — after
  T2.0.
- **T1.8's `test_row_models_match_tables` (already on `main`) asserts every row-model field has a
  matching column in `schema.sql`.**

So T2.0 is required to land a row model whose columns do not exist until the next wave, and an
existing green test correctly rejects it. No amount of fixing inside T2.0's `writes:` scope can
pass the gate: `schema.sql` and `migrations/` are **not** in T2.0's write paths. The fix round
could only have ended red.

Both review-and-fix rounds were spent elsewhere — commit `699541c` ("fix review findings -
unbound `LlmResult[T]`, `check_budget` settings param") addresses real but secondary findings —
and the budget ran out with the structural blocker untouched.

Note the two rounds did land genuine value: invariants pass across 21 code files (up from 14),
ruff is clean, and 285 of 286 tests pass. The single failure is the sequencing defect above.
