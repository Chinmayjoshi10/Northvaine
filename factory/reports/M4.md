### T4.0 root cause (confirmed by the reviewer)

The tests pass in the builder worktree (9 of 9), also with `NEBIUS_API_KEY=dummy` exported,
because the worktree has no `.env`. On `main` the `.env` file sets the key.

The `clean_settings` fixture (`tests/conftest.py`) deletes the Settings env vars and patches
`northvaine.core.settings.get_settings` with `lambda: Settings(_env_file=None)`. But
`northvaine/brain/llm.py` line 48 does `from northvaine.core.settings import ConfigError,
get_settings`, so `llm.get_client()` (line 108) still calls the **original** cached
`get_settings`, which reads `.env` (`env_file=".env"`). So the fixture's "no `.env`" promise
does not reach `llm.py`, and with a real `.env` present the key is found and no error is raised.

Fix (inside T4.0's write scope, test-only, no contract change): in
`tests/brain/test_client_override.py`'s `_no_api_key` fixture, after `clean_settings`, add
`monkeypatch.setattr(llm, "get_settings", settings_module.get_settings)` (the patched one), or
make `clean_settings` itself also patch `northvaine.brain.llm.get_settings`. Then verify with a
dummy `.env` containing `NEBIUS_API_KEY=x` in the worktree before re-merging. The same hole would
affect any later ticket test that relies on `clean_settings` and calls into `llm.py`, so the
conftest-level fix is preferable. This is also the plan's "replay independent of `.env`" goal
(PLAN, Goal and "Env-independent replay"), which T4.1 must prove.
